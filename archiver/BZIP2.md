# Стандартный BZip2 на Goose: формат и память

`gsbzip2.goose` создаёт обычный поток `BZh1`…`BZh9`, который читают Python/libbz2
и обычный 7-Zip. Это отдельный кодек, не переименование `GARC0001`.
Оригинальная реализация MIT; факты формата сверены с исходниками
[компрессора](https://github.com/libarchive/bzip2/blob/master/compress.c),
[декомпрессора](https://github.com/libarchive/bzip2/blob/master/decompress.c)
и [описания рабочих структур](https://github.com/libarchive/bzip2/blob/master/bzlib_private.h).

## API и профиль

```goose
gsbzip2::compress(input, out, level)        // level 1..9; пустой out
gsbzip2::decompress(input, out, limit)      // пустой out; limit 0..67108864
```

Возвращают `bool`; кроме отказа из-за непустого out, ошибка может оставить
частичный результат — его нужно отбросить. `limit` проверяется до расширения
RLE, а не после выделения заявленного объёма. Для 7z передаётся точный OriginalSize,
после декодирования проверяются размер и внешний CRC файла. Внутренние функции,
включая `append_stream`, — детали реализации; append допускает префикс в выходе
для пробного сжатия непосредственно в буфере архива.

Поддерживается один точный современный BZip2-поток, включая несколько блоков,
2..6 таблиц Хаффмана и уровни 1..9. Устаревшие randomized blocks, конкатенация
нескольких самостоятельных потоков, ненулевой padding и байты после EOF
отклоняются. Это ограничения нашего читателя, не обещание чтения любого `.bz2`.
CRC выявляет повреждения, но не аутентифицирует данные.

```text
BZh + ASCII level
  repeat:
    314159265359 (48 bits), block CRC (32), randomized=0 (1), origPtr (24)
    inUse groups (16), used-byte maps (16 per present group)
    table count (3), selector count (15), unary MTF selectors
    delta-coded code lengths (1..20), Huffman data with EOB
177245385090 (48), combined CRC (32), zero padding to byte boundary
```

Цепочка: RLE1 → **циклический** BWT → MTF использованных байтов → RUNA/RUNB →
несколько канонических таблиц Хаффмана, селектор на каждые 50 символов, четыре
прохода уточнения таблиц. CRC BZip2 — старшим битом вперёд, polynomial `04C11DB7`,
init/final XOR `FFFFFFFF`; это **другой CRC**, чем внешний CRC32/ISO-HDLC в 7z.
Combined CRC: rotate-left(previous, 1) XOR block CRC. Контроль `123456789` даёт
`FC891918`. Максимальную длину кодов обеспечиваем перестройкой дерева с
уменьшенными весами; простое обрезание длин нарушило бы префиксность.

## Типы и сроки жизни буферов

`N` — длина блока **после RLE1**, максимум `100000 * level` байтов; размер
десятичный, не КиБ. Длинная серия 259 одинаковых байтов занимает пять байтов.
Поэтому один блок уровня 9 может представлять до 46,62 МБ исходных повторов.
Ограничение декодированного результата обязательно независимо от размера блока.

| Этап | Хранение | Решение |
|---|---|---|
| RLE1 | grow-only `u8`, до N | Неделимые группы; не создаём копию исходного блока |
| Циклическая сортировка | четыре grow-only `u32` массива | Позиции/ранги до 900000; `u64` не нужен, `u16` недостаточен |
| Счётчики сортировки | один из четырёх массивов | После расстановки позиций переиспользуется для новых рангов |
| MTF/RUNA/RUNB | grow-only `u16`, до N+1 символов | Алфавит до 258, поэтому `u8` недостаточен; BWT-байт читается сразу по порядку вращений |
| Huffman | фиксированные таблицы до 6×258 | Частоты/коды `u32`, длины и MTF-списки `u8`, родители дерева `i16` |
| Селекторы | grow-only `u8`, один на 50 символов | Читатель хранит максимум 18002; лишние объявленные селекторы читает и проверяет |
| Inverse BWT | grow-only `u32`, до N | Младшие 8 бит — байт, старшие 24 — следующий индекс; отдельного byte-column нет |
| Inverse RLE1 | сразу итоговый `u8` builder | Проверка лимита до resize; CRC считается по распакованным байтам |

При N ≥ 256 логический пик больших буферов сжатия — **17N байтов**:
RLE1 N плюс сортировка 16N. Точная формула для малого N: `13N + 4*max(N,256)`.
Сортировочные временные массивы выходят из области видимости до наполнения MTF;
на стадии MTF живы примерно 7N байтов, затем около 3N плюс селекторы и
фиксированные таблицы. Это полезная нагрузка массивов, без native stack,
округления страниц, рантайма и входного/выходного файла.

| Уровень | Максимум N | Сжатие: логический пик 17N | Inverse BWT: 4N |
|---:|---:|---:|---:|
| 1 | 100000 | 1,62 МиБ | 0,38 МиБ |
| 3, по умолчанию | 300000 | 4,86 МиБ | 1,14 МиБ |
| 9 | 900000 | 14,59 МиБ | 3,43 МиБ |

У распаковки дополнительно несколько КиБ фиксированных таблиц и до 18 КБ
селекторов. Исходный поток и итоговые байты файла учитываются отдельно.
Выбор уровня не меняет лимит исходного/декодированного файла 64 МиБ.

Goose освобождает место на data stack выходом из области видимости. Следующий
блок/файл использует те же страницы; они не обязаны сразу вернуться ОС. Поэтому
логический пик живых массивов не равен пику commit или working set процесса.
`trim_memory` не вызывается на каждом блоке: это создавало бы повторные page faults.
Пул `reusable` здесь не нужен: освобождение последовательное, без произвольного
порядка. Большие фиксированные массивы на native stack тоже не нужны.

### Встраивание в 7z

- Файл читается сразу в общий `contents`, без промежуточного полного файла.
- Пробное сжатие идёт прямо в `out` архива. Если `packed + 2 >= original`, длина
  откатывается и те же страницы используются для Copy; два байта учитывают более
  длинный ID кодера. Файлы меньше 64 байт сразу используют Copy.
- Для каждого файла отдельный поток; временные буферы не накапливаются по файлам.
- До создания дерева извлечения проверяются все CRC. Затем выбранные сжатые файлы
  декодируются повторно по одному. Это сознательная цена проверки до записи:
  не держим сразу все распакованные файлы. Copy проверяется и пишется по slices.
- Whole-file API всё ещё держит вход и выход. Потоковый I/O и проверка CRC через
  выходной sink позволят сократить эту часть памяти и повторное декодирование.

это не изолированный замер ядра алгоритма. Корпус: повтор README до 2100000 байтов;

байтов (seed 781), один файл против 16 файлов. После устранения полных копий:

| Файлов | Copy: пик WS | BZip2 с откатом в Copy: пик WS |
|---:|---:|---:|
| 1 | 39,86 МиБ | 45,61 МиБ |
| 16 | 39,88 МиБ | 45,57 МиБ |

В локальном одиночном опыте до устранения двух копий пик был 77,04 МиБ, после —

и private commit (PeakPagefileUsage), не выдаёт зарезервированное адресное пространство
за занятые байты.

## Проверка и воспроизведение

```powershell
goose run archiver/bzip2_test.goose
goose build archiver/bzip2_cli.goose -O2 -o build/archiver/gbzip2.exe
./build/archiver/gbzip2.exe c input.txt output.bz2 3
./build/archiver/gbzip2.exe d output.bz2 restored.txt
./build/archiver/gbzip2.exe t output.bz2
python -B archiver/verify_bzip2.py --exe build/archiver/gbzip2.exe --sevenzip PATH_TO_7ZA --out build/archiver/bzip-release
python -B archiver/verify_sevenz_bzip2.py --exe build/archiver/g7z.exe --sevenzip PATH_TO_7ZA --out build/sevenz-layout/bzip-release
python -B archiver/bench_bzip2_memory.py --exe build/archiver/gbzip2.exe --corpus archiver/fixtures/memory-text.txt --out build/archiver/bzip-memory
python -B archiver/bench_sevenz_memory.py --exe build/archiver/g7z.exe --out build/archiver/archive-memory
```

Кодек переносим; оба новых CLI сейчас Windows x64 и используют Unicode Win32
аргументы через `gswinargs.goose`. Алгоритм работает на Goose без вызова libbz2,
7-Zip или рукописных C-помощников. Внешние программы нужны только тестам.
Для сверки нужен полный официальный **7za**, а не ограниченный 7zr без BZip2.
Проверено с 7za 26.05 x64, SHA-256
`7ddf0a3bc451e166679296be630d6f0573eb386159c04184761c43020c484291`.

Проверки оптимизированной и debug-сборок: 69 потоков Goose → libbz2, 69 в обратную
сторону, 15 проверок 7-Zip, 48 отказов на повреждениях и 150 мутаций; для 7z —
четыре наших архива (Copy и уровни 1/3/9), три архива BZip2 от 7-Zip, два варианта
PackInfo CRC, девять отказов до создания дерева и четыре выборочных извлечения.
Имена каталогов теста, аргументы и имена внутри архива включают кириллицу и emoji;
проверяется точное MTime файлов и каталогов. Исходные Copy-проверки остаются отдельными.

## Следующие резервы

1. Циклическая сортировка сейчас prefix doubling с counting sort, O(N log N).
   Старый SA-IS с терминатором не заменяет её напрямую. Нужен специальный циклический
   sorter с независимыми проверками периодических строк, прежде чем обещать ускорение.
2. Дерево Хаффмана выбирает минимальные веса линейным поиском. Фиксированная min-heap
   уменьшит вычисления, не потребует динамической памяти; измерить на множестве блоков.
3. Декодер Хаффмана читает по биту; таблица быстрого префикса требует немного
   фиксированной памяти, но должна оправдать себя измерениями.
4. Потоковый файловый слой/выходной sink важнее дальнейшего уменьшения таблиц,
   если задача — большие архивы при ограниченной памяти.
