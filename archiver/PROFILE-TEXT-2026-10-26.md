# Профиль Zstd на обычном тексте — 2026-10-26

Главный резерв уровня 3 — хеширование и обращения к таблицам внутри
`parse_dfast`, затем проверка короткого кандидата с поиском на байт вперёд.
Переписывать буферы литералов первым шагом эти измерения не предлагают.
Это профиль нашей реализации, а не пофункциональный профиль разрыва с libzstd.

## Методика и границы точности

Текущий `archiver/zstd.goose`, SHA-256
`37c13829c87108033e9dbe8d1a74b78c4419eb5814d251897c75cc881dcd3d7b`.
Рабочая библиотека не менялась. Goose `-O2`, GCC 16.1.0 `-O2 -g`:
оптимизированная release-сборка с отладочными символами, без `--debug` и
без отключения inline. Для отдельной сборки сгенерирован C с runtime
в одном файле (`--standalone`); это вспомогательная профилировочная сборка.

Windows x64: внешний сборщик приостанавливает только основной поток
собственного дочернего benchmark, получает RIP через `GetThreadContext`
и сразу возобновляет поток. Интервал случайный: 0,7–2,3 мс. Адреса
нормализованы с учётом ASLR и разрешены через GCC `addr2line`, включая inline.
Сохранены адреса, исходный C, дизассемблирование и хеши сборки.

Три запуска примерно по 10 секунд на каждый вход: Alice (174311 байтов),
Sherlock (607606 байтов) и сохранённая Markdown-документация репозитория.
Байты не повторялись для увеличения файла. Уровень 3, API с сохраняемым
контекстом; по три прогрева. Профилировался длинный цикл сжатия.
Во время профиля не запускались сборки или тесты кодека.

Получено **49773 сэмпла внутри EXE**: 16275 Sherlock, 16858 Alice,
16640 Markdown. Ещё 326 адресов вне EXE исключены из знаменателя;
8 неудачных попыток получения контекста также не учтены. Все дочерние
процессы завершились успешно. Итоговые потоки независимо распакованы
официальным zstd 1.5.7 с побайтовым сравнением.

Проценты ниже — доли выборок инструкций, **не замеры latency/cache misses
или времени отдельных C/Goose-строк**. Компилятор переставляет инструкции;
адрес после загрузки может относиться к следующему выражению исходника.
Поэтому соседние инструкции объединены в группы операций, а не выданы
за отдельную стоимость хеш-умножения или промаха кеша. По стеку вызовов
не выполнялось полное разворачивание: внешние не-inline helpers показаны
отдельно. Из-за приостановок длительность профилируемого процесса нельзя
использовать как результат benchmark скорости.

Точечные маленькие различия не следует трактовать как отдельный выигрыш.

## Частота ветвей — отдельное измерение

В копии модуля под `build/` добавлена отдельная функция со счётчиками.
Она не используется для процентов времени. На каждом блоке её sequences,
литералы, итоговый anchor и repeat offsets сравниваются с неизменённым
`parse_dfast`. Счётчик собран с `--debug`; сравнения прошли на всех пяти
входах ниже. Проверено и равенство суммы literal/matched байтов длине входа.

| Вход | Успешный long-lookahead среди попыток | Совпадения короче 16 байт |
|---|---:|---:|
| Alice | 12,8% | 96,5% |
| Sherlock | 16,0% | 98,1% |
| Markdown | 12,0% | 93,0% |
| Исходники | 13,8% | 86,0% |
| Синтетические 256 слов, seed 42 | 93,9% | 99,6% |

Знаменатель первой колонки — входы в ветку короткого кандидата, где
проверяется длинный кандидат на следующем байте. Это не доля всех probes.
Неуспех long-lookahead не означает полного неуспеха поиска: после него
парсер использует короткое совпадение.

Например, Sherlock: 118672 основных probes, 42580 попыток lookahead,
6832 успеха lookahead, 72148 итоговых sequences. Короткий lookahead
успешен гораздо реже, чем на искусственном словарном тексте; это объясняет,
почему оптимизация того корпуса плохо переносится на обычную прозу.

## Следующие эксперименты

1. **Сократить работу с хешами и зависимыми обращениями к таблицам.**
   Сначала проверить сохранение тех же индексов с объединёнными сдвигами
   (`>>47`, затем `>>lshift` → один unsigned-сдвиг на `47+lshift`;
   аналогично для short hash), вычисляя общие значения вне горячего цикла.
   Это кандидат для измерения, не доказанное ускорение. Затем отдельно
   исследовать обновления после совпадения; их сокращение может менять плотность.
2. **Исследовать цену lookahead.** Группа короткого кандидата занимает
   11–15% всего сжатия. Нельзя просто отключить её: на обычном тексте
   полезны 12–16% попыток, на словарном — почти 94%. Любая адаптация требует
   парных замеров скорости/размера и проверки обоих типов входа.
3. **После parser — `encode_sequences` и `bitw_put`.** Вместе около 13–14%
   сэмплов. Это второй эшелон, а не основной источник текущего разрыва.

`match_at`, буферы литералов и checksum не первые кандидаты. Декодер и
уровни 4–19 этим профилем не измерялись. Точных пофункциональных отношений
скорости с libzstd данный эксперимент не устанавливает.

## Локальное воспроизведение

Всё вспомогательное находится под ignored `build/zstd-profile/`:

- `bench.c`, `bench.exe`, `disassembly.txt` — сборка и инструкции;
- `sample.py`, `resolve.py`, `summarize.py` — сбор и разбор профиля;
- `sherlock-final/`, `alice-final/`, `docs-final/` — сырые и разрешённые адреса;
- `summary.json`, `counts.json`, `manifest.json` — сводка, счётчики и хеши;
- `counts/`, `counts.exe`, `make_counts.py` — изолированная проверенная копия со счётчиками.

Пример из корня репозитория с установленными инструментами:

```powershell
python -B build/zstd-profile/sample.py --exe build/zstd-profile/bench.exe --input build/zstd-text/sherlock.bin --out build/zstd-profile/sherlock-final --seconds 10 --runs 3
python -B build/zstd-profile/resolve.py sherlock-final alice-final docs-final
python -B build/zstd-profile/summarize.py
```

Пути runtime/toolchain зависят от машины и записаны в драйверах/manifest.
