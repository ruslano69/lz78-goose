## Методика и ограничения

Windows x64; Goose `-O2`, GCC 16.1.0; libzstd 1.5.7, бинарная библиотека с неизвестными флагами компиляции. Сравниваются готовые реализации, а не языки на одинаковых настройках компилятора. Используется текущее дерево исходников, включая незакоммиченное кэширование Huffman. SHA-256 `archiver/zstd.goose`: `de3cf6c57605d37ead65c3c093eb14563c59f200dae1de8d005e281d1a7a8f07`.

Для каждого набора libzstd создаёт отдельный кадр выбранного уровня с checksum и без потоков; checksum проверяется при распаковке обеими сторонами. Ровно те же байты кадра и исходного файла используются для обеих реализаций. На каждую точку — пять чередующихся пар замеров и по три прогрева; показана медиана. Чтение, запись и запуск процесса исключены из таймера. Каждая серия проверяет восстановленные байты.

libzstd использует повторно выделенный контекст и заранее выделенный выход; наша реализация создаёт контекст декодера при каждом вызове и повторно использует выходной буфер. Время вызовов libzstd через Python ctypes включено и особенно заметно для быстрых случаев. Частота CPU, кэш и отсутствие фиксации ядра могут влиять на результаты.

Собственные `gzstd.exe` и `g7z.exe` собраны из проекта; Sherlock и исходники — сохранённые файлы без повторения. «256 слов» — синтетический словарь из прежнего сравнительного набора; случайные данные и нули — по 1 МиБ. Синтетические случаи помогают отличить сжатые блоки от практически сырого и RLE-выхода, но не представляют все реальные файлы.

Драйвер, точные входные кадры, хеши, все отдельные замеры и метаданные сохранены в ignored `build/zstd-decode-levels/` (`measure.py`, `results.json`). Для повтора из корня запустить `measure.py` через доступный Python после сборки `archiver/bench_zstd.goose` в `build/zstd-decode-levels/bench.exe`; пути DLL и входных файлов локальны для этой машины.
